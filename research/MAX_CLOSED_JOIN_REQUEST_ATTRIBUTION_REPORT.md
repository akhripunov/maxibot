# MAX: точная атрибуция заявки в закрытый канал

Дата проверки: 2026-08-11. Контур: собственный тестовый канал `Твой Петербург`, MAX Web, официальный Bot API и локальный MAXIBOT.

## Итог

**PARTIAL / точная атрибуция не доказана.** Прямой маршрут `landing → native invite закрытого канала` реализуем и не требует бота, mini app или дополнительного экрана. Но доступный объект заявки/участника содержит идентификатор пользователя, а не идентификатор invite или visitor. Поэтому связку

```text
visitor_id / yclid → конкретная заявка → MAX user_id → approved member
```

нельзя считать `EXACT` без дополнительного серверного поля MAX.

Разрешённые статусы для текущего прямого маршрута: `SINGLE_CANDIDATE`, `AMBIGUOUS`, `UNATTRIBUTED`. Временная близость перехода и заявки не является доказательством.

## Что реально увидено в MAX

Тестовый канал был приватным, с включёнными заявками на вступление. MAX Web показывал одну native invite-ссылку формата `https://max.ru/join/<opaque-token>` и раздел новых заявок. Отдельный invite ID, статистика использования ссылки и source/ref в UI не отображались.

При чтении списка заявок через WebSocket наблюдалась операция `JOIN_REQUEST` с запросом по `chatId`. Ответ имел верхний уровень `members`; фактический объект содержал контакт пользователя примерно в таком виде:

```json
{
  "members": [
    {
      "contact": {
        "id": "[MAX_USER_ID_REDACTED]",
        "updateTime": "...",
        "registration": "...",
        "names": [{"name": "...", "firstName": "..."}],
        "type": "...",
        "options": "...",
        "accountStatus": "...",
        "presence": "..."
      }
    }
  ]
}
```

В наблюдаемом объекте не было `request_id`, `invite_id`, `invite_token`, `source`, `ref`, `start_param`, `link_id`, `created_at` или visitor/click ID. `chatId` был только параметром запроса, а не доказательством источника конкретной заявки.

Официальный `Update` документирует `user_added` как добавление или переход пользователя по ссылке, но перечисляет только `update_type`, `timestamp`, `chat_id`, `user` и `is_channel`; invite/source-поля там не заявлены. [Документация Update](https://dev.max.ru/docs-api/objects/Update)

Официальный `GET /chats/{chatId}/members` возвращает `ChatMember`, включая ID пользователя и данные членства; параметр `user_ids` позволяет проверить конкретного пользователя, но результат не содержит источник invite. Метод требует, чтобы бот был администратором канала. [Документация метода members](https://dev.max.ru/docs-api/methods/GET/chats/-chatId-/members)

## A/B и одобрение

Полный эксперимент `User A → Invite A`, `User B → Invite B` не завершён: в доступном сеансе был один авторизованный MAX-аккаунт. Также UI показал одну активную native invite-ссылку; наличие независимых A/B invite в тестовом канале не подтверждено.

Ручное одобрение в MAX Web описано официально: владелец или администратор нажимает галочку, после чего пользователь добавляется в канал. Публичного Bot API метода чтения заявки с invite-source или программного approve/reject в доступной документации не найдено. [Управление заявками в приватном канале](https://dev.max.ru/docs/channels/manage)

Следовательно, verdict для публичного API: **автоматическое одобрение — NO PUBLIC METHOD**. Внутреннее Web-действие может существовать, но в этом тесте не вызывалось и не принимается как стабильный контракт.

## Изменение MAXIBOT

`/traffic-test` теперь ведёт напрямую через `307` на настроенный `https://max.ru/join/...` из `TrafficProfile.target_url`. В этот маршрут не добавляются `startapp`, бот, mini app или промежуточный CTA в MAX. UTM/yclid сохраняются в `TrafficVisit` до redirect; native MAX invite получает только собственную ссылку.

Старая startapp-логика предыдущего PoC оставлена как отдельный экспериментальный код и не используется в закрытом direct-invite маршруте. Для direct visits `startapp_token` не создаётся, чтобы исключить ложный `EXACT` через старую ветку идентификации.

## TeleGraphyx и Yandex Direct

Публичный black-box пример TeleGraphyx ранее показал маршрут через MAX-бота с `startapp`, а не через native invite закрытого канала. Это не доказывает наличие или отсутствие отдельного закрытого режима в авторизованном кабинете TeleGraphyx; для него нужен собственный тестовый проект.

Будущая цепочка Yandex Direct может передать `yclid` до landing и сохранить его локально, но финальная связь с заявкой MAX всё равно останется временной кандидатурой, пока MAX не отдаёт server-side invite/source ID или TeleGraphyx не предоставляет такой ID через свой backend.

## Критерий полного успеха

Полный `YES` не достигнут. Он будет достигнут только если один и тот же server-side идентификатор подтвердит `visitor → request → user_id`, затем ручное/автоматическое одобрение подтвердит `user_id → member`, без intermediary.
