# MAX: атрибуция вступления по invite-ссылке

Дата проверки: 2026-08-11. Область: собственный канал `Твой Петербург`, официальный MAX Web, публичный MAX Bot API.

## Вывод

Публичный MAX Bot API не предоставляет доказуемую связь `invite token → user_id`.

Событие `user_added` содержит факт добавления пользователя в чат/канал, но в описанной схеме нет `invite_id`, `invite_token`, `source`, `referrer` или эквивалентного поля. Запрос списка участников также возвращает `join_time` и данные пользователя, но не источник вступления.

Это означает, что по публичному Bot API можно надёжно сохранить:

```text
chat_id + user_id + timestamp
```

но нельзя корректно перевести это в:

```text
invite_id/token + user_id
```

Временная близость перехода и вступления остаётся только `SINGLE_CANDIDATE`/`AMBIGUOUS` и не должна отправляться как реальная конверсия. Это соответствует текущей защите в `app/traffic/attribution.py`.

## Что проверено в MAX Web

- Открыт собственный канал `Твой Петербург` в официальном Web-клиенте.
- В профиле канала открыта форма «Пригласить по ссылке».
- UI показывает одну активную ссылку вида `https://max.ru/join/<opaque-token>`; отдельный `id` invite не отображается.
- В форме доступны копирование, отправка в MAX, QR-код и переключатель заявок на вступление. Публичного списка использовавших ссылку или статистики по ссылке не обнаружено.
- При обновлении профиля/формы наблюдались бинарные WebSocket frames. В видимых ответах присутствовали данные канала и участников; отдельные поля источника вступления не обнаружены.
- Полный A/B-эксперимент `User A → Invite A`, `User B → Invite B` не завершён: в текущем сеансе доступен один авторизованный MAX-аккаунт, а второй тестовый аккаунт не был подключён. Поэтому этот отчёт не утверждает, что приватный backend MAX принципиально никогда не передаёт источник — только то, что это не доказано через доступный Web-клиент и публичный API.

## Что следует из официальной документации

1. Объект `Update` перечисляет `user_added` как событие добавления/перехода по ссылке, но его поля — `update_type`, `timestamp`, `chat_id`, `user`, `is_channel`; invite-идентификатора в схеме нет.
2. `GET /chats/{chatId}/members` возвращает `ChatMember`, включая `user_id` и `join_time`; поля invite/source в объекте нет.
3. Документированный метод получения информации о канале по ссылке относится к публичной ссылке канала (`GET /chats/{chatLink}`), а не к invite-статистике или списку пользователей, пришедших по invite.
4. Документация управления приватным каналом описывает заявки на вступление и их ручное одобрение, но не описывает передачу invite-id в Bot API update или API чтения заявок.

## Практическое решение для MAXIBOT

Оставить каналовую регистрацию участника как факт без автоматической EXACT-атрибуции. Для точной атрибуции использовать только контролируемые точки, где MAX передаёт payload приложению, например deeplink на бота с `start`-параметром, либо ждать официального API поля invite/source. Channel invite сам по себе для этой задачи сейчас недостаточен.
