# ТЗ ДЛЯ CODEX
# Единая архитектура релизов MAXIBOT и GPoint — FINAL

**Статус:** целевая архитектура утверждена владельцем.
**Задача:** реализовать новую систему релизов, безопасно перевести оба проекта и полностью удалить устаревшую исполняемую релизную инфраструктуру.

## 1. Главная цель

Полностью заменить существующие сложные системы релизов MAXIBOT и GPoint стандартной архитектурой на готовых инструментах GitHub и Docker.

**Репозитории:**

- MAXIBOT: https://github.com/akhripunov/maxibot
- GPoint: https://github.com/akhripunov/gpoint

Новая система должна быть:

- Простой — минимум собственного кода, workflows и зависимостей.
- Надёжной — обязательные проверки перед production.
- Быстрой — кеширование, параллельные тесты, сборка только необходимых компонентов.
- Автоматической — одна команда владельца запускает полный разрешённый релиз.
- Универсальной — одинаковая стандартная архитектура для разных проектов.
- Независимой — каждый проект сохраняет собственные workflows, секреты, образы и production-состояние.
- Поддерживаемой — без собственных Release Controller и необходимости постоянно ремонтировать саму систему релизов.

**Конечный пользовательский сценарий:**

Владелец говорит Codex:

«Делай релиз».

Или:

«Исправь задачу ME-50 и выкати».

После этого в рамках подтверждённой авторизации Codex запускает соответствующий GitHub Actions workflow, который выполняет обязательные проверки, собирает необходимые образы, публикует их в GHCR, устанавливает на VPS, проверяет production и фиксирует результат.

**Второго ручного подтверждения не требуется**, если исходная команда владельца действительно разрешает полный цикл для соответствующего проекта, изменений и рисков.

Не считать это разрешением на произвольные изменения или обход действующих production-защит.

## 2. ОБЯЗАТЕЛЬНЫЙ ПРИНЦИП — NATIVE FIRST

**Главное архитектурное требование:**

> Перед реализацией каждого этапа проверять, предоставляет ли GitHub или Docker нужную возможность штатно. Если предоставляет — использовать её напрямую, не создавать промежуточный скрипт, дополнительный workflow, сервис или отдельное хранилище состояния. Минимизировать количество workflows, шагов, зависимостей и конфигураций без ослабления production-защит.

Это правило обязательно для каждого технического решения.

Приоритет инструментов:

1. Встроенные возможности GitHub и Docker.
2. Официальные GitHub Actions и Docker Actions.
3. Стандартные OpenSSH, Linux и Docker CLI.
4. Уже существующие необходимые тесты и проверки приложения.
5. Минимальная собственная логика исключительно там, где штатных возможностей недостаточно.

**Запрещено создавать:**

- Release Controller V6 или его аналог.
- Собственный deployment orchestrator.
- Дополнительную службу управления релизами.
- Собственную базу production state.
- Собственный registry.
- Release ledger.
- Отдельный релизный API.
- Собственную панель релизов.
- Дублирующие workflow для одного действия.
- Промежуточные архивы Docker-образов как отдельный transport.
- Скрипты, просто дублирующие возможности Docker или GitHub.

Если для безопасности необходима небольшая проектная проверка, её разрешено сохранить или реализовать.

**Минимум собственного кода — не абсолютный ноль строк.**

Не заменять нужную проверку безопасности отсутствием проверки ради формального сокращения файлов.

## 3. УТВЕРЖДЁННАЯ АРХИТЕКТУРА — 9 ЭТАПОВ

### Этап 1. Код — разработка

**Codex + Docker Plugin + Git + GitHub.**

- MAXIBOT разрабатывается в собственном репозитории.
- GPoint разрабатывается в собственном репозитории.
- GitHub хранит исходный код и историю изменений.
- Codex использует доступные инструменты Docker при необходимости.
- Локальная разработка и публикация соблюдают действующие OWNER-правила каждого репозитория.

Не добавлять новый инструмент управления исходным кодом.

### Этап 2. CI — тестирование

**GitHub Actions + actions/checkout + actions/setup-python / actions/setup-node + pytest / pnpm / Playwright.**

Использовать штатное кеширование зависимостей.

Запускать только необходимые для соответствующего проекта инструменты.

**MAXIBOT:**

- MAX Bot API.
- Подключение и управление каналами.
- Учёт подписчиков.
- Атрибуция Яндекс Директа.
- API и Poller.
- PostgreSQL и Redis.
- Alembic-миграции.
- Критические функции рекламного трафика.
- Существующие обязательные проверки безопасности.

**GPoint:**

- Node.js и TypeScript.
- Python и pytest.
- API, Bot и Worker.
- AGATA.
- GSales.
- Eros.
- Mini App.
- Playwright, где требуется.
- Миграции и интеграционные проверки.
- Совместимость компонентов и защита данных.

**Оптимизация тестирования:**

1. Измерить фактическое время каждого набора тестов.
2. Определить обязательные и необязательные проверки.
3. Найти доказанное дублирование.
4. Разделить быстрые, интеграционные и тяжёлые тесты.
5. Выполнять независимые проверки параллельно.
6. Применять выборочное тестирование по затронутым компонентам.
7. При изменении общих зависимостей запускать полный необходимый набор проверок.
8. Сохранить обязательные release gates перед production.

Не удалять тесты ради скорости без подтверждения, что они действительно избыточны.

Не писать собственный сложный анализатор влияния изменений, если достаточно стандартных средств GitHub и существующих инструментов проектов.

### Этап 3. Build & Push — Docker-сборка

**Официальные Docker Actions:**

- `docker/setup-buildx-action`
- `docker/login-action`
- `docker/build-push-action`
- Docker BuildKit Cache (`type=gha`)

Обязательные условия:

- Сборка выполняется на GitHub-hosted runner.
- Production-образы не собираются на VPS.
- Используется кеш Docker-слоёв.
- Неизменившиеся слои повторно используются.
- Собираются только необходимые образы, когда независимость компонентов подтверждена.
- Новые образы публикуются непосредственно в GHCR.
- Сохраняется точный digest опубликованного образа.
- Не создаются промежуточные архивы образов и дополнительные хранилища.

`docker/metadata-action` не использовать без доказанной необходимости. Для обычного SHA-тегирования достаточно стандартных параметров `docker/build-push-action`.

Проверить и при необходимости оптимизировать Dockerfiles обоих проектов.

Не менять устройство приложения только ради косметического сокращения Dockerfile.

### Этап 4. Registry — хранение

**GitHub Container Registry (GHCR).**

Для каждого production-образа использовать:

- точный Git SHA;
- неизменяемый OCI image digest;
- проверяемую связь с успешной сборкой.

Production устанавливает конкретный digest, а не `latest`.

Не использовать параллельное хранение Docker-образов в GitHub Releases, Actions Artifacts или на Mac.

Docker должен повторно использовать слои, которые уже присутствуют на VPS.

Сохранять необходимые проверенные rollback-образы в соответствии с политикой хранения.

Не создавать собственный каталог образов или базу истории установок.

### Этап 5. Release — разрешение и запуск

**Codex + GitHub API + `workflow_dispatch`.**

Codex получает прямую команду владельца.

Перед запуском production проверяет:

- проект;
- действительную авторизацию;
- scope изменений;
- точный Git SHA кандидата;
- соответствие текущему разрешённому источнику;
- обязательные risk contracts;
- отсутствие конфликтующего активного релиза.

Если команда разрешает полный цикл и проверки проходят, Codex запускает GitHub Actions без дополнительного ручного подтверждения.

Обычный push в `main` не разрешает production.

Не использовать отдельный Release Controller для запуска или координации workflows.

Не создавать дополнительную очередь релизов.

Использовать стандартный GitHub API или GitHub CLI только там, где действительно требуется запустить workflow либо проверить его состояние.

Остальные действия выполняет GitHub Actions.

При изменившемся scope, отсутствии необходимой авторизации или неопределённом состоянии production релиз блокируется.

**Важно:** само это ТЗ утверждает техническую архитектуру, но не отменяет специальные ограничения существующих политик на публикацию, изменение релизной инфраструктуры, секретов, миграций и production cutover.

Если отдельный риск-контракт ещё необходим, подготовить результат в пределах доступной авторизации и не выполнять защищённую операцию до её разрешения.

### Этап 6. GitHub Deployments — история релизов

**GitHub Environment (`production`) + GitHub Actions `concurrency`.**

Использовать штатную интеграцию GitHub Environments с Deployments.

Не создавать собственный сервис управления статусами.

Не писать отдельный клиент GitHub Deployments API, если GitHub автоматически выполняет необходимую операцию.

Требования:

- Каждый проект использует собственное production environment.
- Фиксируются SHA, workflow run и результат установки.
- Deployment job завершается успешно только после обязательных проверок.
- Ошибка Verify приводит к неуспешному результату job.
- Фактическое состояние VPS проверяется независимо от GitHub Deployment.

Использовать `concurrency` с `cancel-in-progress: false` для production-операций, если остановка активного релиза небезопасна.

Не включать обязательное дополнительное подтверждение через GitHub Environment, если владелец уже разрешил полный цикл и это не требуется действующей политикой безопасности.

### Этап 7. Deploy — установка

**Собственный минимальный GitHub Actions workflow каждого проекта + OpenSSH + Docker Compose V2.**

**Общий Reusable Workflow (`workflow_call`) НЕ использовать.**

**Отдельный репозиторий `release-workflows` НЕ создавать.**

MAXIBOT и GPoint используют одинаковые штатные технологии, но сохраняют собственные небольшие и независимые workflows.

**Требования к Deploy:**

- Установка с GitHub-hosted runner.
- Подключение к VPS через OpenSSH.
- Обязательная проверка SSH host key.
- Минимальные SSH-права.
- Никаких секретов в логах.
- Получение образов из GHCR.
- Установка по проверенному OCI digest.
- Обновление только выбранных компонентов.
- Сохранение существующих Docker volumes и сетей.
- Не пересоздавать базы данных и чужие сервисы без отдельной необходимости.
- Использовать стандартные команды Docker Compose.
- Применять `--no-deps`, когда это безопасно для соответствующего сервиса.
- Не использовать сторонние SSH Actions, если достаточно OpenSSH.

**Защита общего VPS:**

GitHub Actions concurrency ограничивает операции внутри репозитория, но не координирует два независимых репозитория.

Использовать стандартный Linux `flock` там, где есть риск конфликта при общей серверной операции.

Убедиться, что блокировка действует на фактическое выполнение операции, а не только на кратковременный запуск команды.

Не создавать отдельный распределённый lock-сервис.

Никакой релиз GPoint не должен изменять состояние MAXIBOT, и наоборот.

### Этап 8. Verify — проверка production

**Docker Healthchecks + `docker inspect` + `curl` + существующие smoke-тесты.**

Проверять:

- установленный Git SHA;
- фактический image digest;
- готовность API;
- состояние PostgreSQL;
- нужные миграции;
- состояние Workers;
- критические бизнес-функции;
- отсутствие ошибок, требующих блокировки.

Не считать Docker `running` достаточным доказательством готовности приложения.

**При ошибке:**

1. Определить фактическое состояние.
2. Не фиксировать Deployment как успешный.
3. Проверить безопасность возврата прежней версии.
4. Выполнить допустимый откат, если он безопасен.
5. Если состояние неопределённое — остановить дальнейшие изменения.

Никаких слепых повторных Deploy.

Не считать откат Docker-образа автоматическим откатом PostgreSQL.

### Этап 9. Operate — эксплуатация

**Docker Restart Policies + существующий мониторинг + PostgreSQL backup + внешнее хранилище резервных копий + проверка восстановления.**

Сначала изучить уже установленное ПО обоих проектов.

Не устанавливать новые системы мониторинга и резервного копирования без необходимости.

Использовать готовые и проверенные инструменты.

Проверить:

- автоматические перезапуски контейнеров;
- мониторинг доступности;
- мониторинг критических фоновых процессов;
- наличие резервных копий;
- защищённое внешнее хранение;
- фактическую возможность восстановления;
- доступность предыдущих совместимых образов.

Новая релизная архитектура не должна ухудшать существующую защиту данных.

## 4. Единая архитектура без общего Reusable Workflow

**Это окончательное решение.**

Не создавать обязательный общий GitHub Reusable Workflow.

Не создавать отдельный центральный репозиторий релизной инфраструктуры.

Вместо этого:

- MAXIBOT использует собственные минимальные GitHub Actions workflows.
- GPoint использует собственные минимальные GitHub Actions workflows.
- Оба проекта используют одинаковые официальные инструменты GitHub и Docker.
- Каждый проект самостоятельно управляет тестированием, сборкой, установкой и Verify.
- Секреты и production-авторизации строго разделены.

Не пытаться насильно унифицировать уникальную логику приложений.

**Единая система означает единый технологический стандарт, а не общий исполняемый контроллер.**

В будущем при появлении множества однотипных проектов можно отдельно пересмотреть необходимость Reusable Workflows. В текущей реализации их не добавлять.

## 5. Обязательные условия MAXIBOT

Перед изменениями изучить текущую production-конфигурацию.

Сохранить:

- MAX Bot API;
- единственный активный MAX Poller;
- работу каналов;
- подписки;
- рекламную атрибуцию;
- PostgreSQL;
- Redis;
- Caddy;
- файлы и volumes;
- существующие производственные данные.

**Критическое правило: одновременно не должны работать два production MAX Poller.**

Проверить правильный порядок обновления API и Poller.

Не использовать стратегии обновления, которые временно запускают второй активный Poller.

Перед миграциями проверять Alembic target, обязательные backup gates и совместимость с возможным откатом.

Не допускать потери событий или повреждения данных из-за обновления.

## 6. Обязательные условия GPoint

Сохранить действующую архитектуру:

- API;
- Bot;
- Worker;
- AGATA;
- GSales;
- Eros;
- Mini App;
- PostgreSQL/Redis;
- Caddy;
- существующие Docker-сети и volumes;
- отдельный Mac Worker.

Не объединять все компоненты GPoint в один Docker-образ ради упрощения релиза.

Поддержать независимое обновление компонентов, где это предусмотрено архитектурой.

**UI-only релиз Mini App не должен требовать полной пересборки backend**, если отсутствует реальная зависимость.

Сохранить специальные проверки AGATA, Eros, GSales, миграций, ACL, совместимости Workers и целостности данных.

Серверный Deploy не должен зависеть от Mac runner.

При этом действующий Mac Worker, который выполняет функции самого GPoint, нельзя удалять только потому, что мы убираем Mac runner из релизов.

## 7. Безопасный переход на новую систему

**Старую систему необходимо полностью вывести из эксплуатации и удалить из активной конфигурации.**

Однако удаление допускается только после успешного перехода соответствующего проекта.

### Фаза A. Read-only аудит

Для обоих проектов:

1. Проверить актуальные репозитории и `main`.
2. Изучить действующие `AGENTS.md` и release authorization policy.
3. Проверить активные Actions и незавершённые операции.
4. Изучить Docker Compose и существующие сервисы.
5. Зафиксировать фактический production baseline.
6. Проверить базы данных, volumes и резервные копии.
7. Составить перечень всех механизмов V3/V4/V5.
8. Измерить фактическое время текущих релизов.
9. Определить, какие защитные проверки необходимо сохранить.

Не считать устаревшим всё, что имеет название `release` или `preflight`.

Отделить ненужную оркестрацию от полезных проверок безопасности.

### Фаза B. Реализация

Создать новые минимальные GitHub Actions workflows отдельно в MAXIBOT и GPoint.

Для каждого проекта организовать:

- CI;
- Docker BuildKit;
- GHCR;
- разрешённый запуск;
- GitHub Environment;
- SSH + Docker Compose;
- Verify;
- безопасный rollback.

Минимизировать число отдельных workflows.

Не создавать дополнительный reusable workflow, контроллер или сервис.

Не включать новый production pipeline параллельно со старым так, чтобы оба могли одновременно управлять VPS.

### Фаза C. Проверка

Проверить на безопасном изолированном окружении:

- корректность YAML;
- тесты;
- BuildKit Cache;
- публикацию GHCR;
- точный digest;
- SSH host verification;
- права доступа;
- Compose update;
- серверную блокировку;
- запрет параллельных конфликтующих релизов;
- отсутствие двух MAX Poller;
- компонентные релизы GPoint;
- failure и rollback;
- сохранность volumes;
- отсутствие влияния на соседний проект.

Не выдавать dry-run за успешный production-релиз.

### Фаза D. Production cutover

Переводить проекты последовательно.

Перед каждым переключением проверить:

- действительность OWNER-авторизации;
- разрешённые риски;
- неизменность scope и baseline;
- успешные тесты;
- наличие проверенного Docker-образа;
- резервные копии;
- отсутствие конфликтующих релизов;
- возможность восстановления.

После установки подтвердить фактическое production-состояние.

Только после успешного Verify считать проект переведённым на новую систему.

### Фаза E. Удаление старой системы

После подтверждения нового production pipeline соответствующего проекта:

**Удалить заменённые исполняемые механизмы:**

- старые Release Controllers;
- устаревшие Prepare/Deploy workflows;
- ненужные автоматические preflight controllers;
- отдельные recovery controllers, заменённые штатными средствами;
- неиспользуемые release scripts;
- ненужные механизмы хранения release state;
- прежние архивные Docker transports;
- старые Mac runner jobs для серверного Deploy;
- неиспользуемые зависимости;
- устаревшие конфигурации;
- неактуальные ссылки и инструкции.

Провести поиск оставшихся зависимостей от старой системы.

**Не оставлять второй активный релизный механизм.**

Но не удалять:

- Git history;
- необходимую историю аудита;
- рабочие данные;
- базы данных;
- резервные копии;
- Docker volumes;
- полезные тесты;
- обязательные production gates;
- компоненты, которые не относятся к релизной инфраструктуре.

После удаления проверить, что оба проекта продолжают корректно работать.

## 8. Безопасность и полномочия

Придерживаться принципа минимальных прав.

GitHub Actions для непроверенного кода не должны иметь доступ к production-секретам.

Все используемые Actions закреплять за проверенными неизменяемыми версиями.

Не использовать непроверенные shell inputs.

Не передавать произвольные пользовательские команды непосредственно в серверный shell.

Сохранять независимые секреты MAXIBOT и GPoint.

Любые изменения в release authorization policy, security controls, миграциях и production-инфраструктуре выполнять только в пределах действительной авторизации владельца и необходимых risk contracts.

Не обходить действующие ограничения репозиториев ради упрощения.

**Одна авторизация полного разрешённого цикла — да. Отсутствие авторизации — нет.**

## 9. Производительность

До и после миграции измерить:

- ожидание runner;
- CI;
- установку зависимостей;
- Docker Build;
- Docker Push;
- Docker Pull;
- Compose update;
- Verify;
- полное время релиза.

Особое внимание уделить устранению ожиданий Mac runner и старых контроллеров.

Использовать кеширование и параллельность, но не отключать критические проверки.

Не обещать конкретное ускорение до фактических измерений.

Сравнение выполнить отдельно для MAXIBOT и GPoint.

## 10. Аудит простоты после реализации

Проверить каждый созданный release-файл и workflow.

Для каждого компонента ответить:

1. Зачем он нужен?
2. Есть ли уже штатная возможность GitHub или Docker?
3. Можно ли реализовать то же самое простой конфигурацией?
4. Дублирует ли он другую операцию?
5. Не создаёт ли новый источник истины?
6. Можно ли его удалить без потери обязательной безопасности?

Устранить подтверждённое дублирование.

Предпочитать простой стандартный инструмент сложной собственной реализации.

Не создавать общий Reusable Workflow только ради унификации.

## 11. Критерии приёмки

**Работа завершена только при выполнении всех условий:**

- [ ] MAXIBOT использует новую релизную систему.

- [ ] Каждый проект имеет собственный минимальный GitHub Actions pipeline.

- [ ] Базы данных, volumes и резервные копии сохранены.
- [ ] Проверки production подтверждают фактический результат.

## 12. Финальный отчёт Codex

Подготовить один понятный итоговый отчёт.

**ARCHITECTURE**

Какие GitHub и Docker инструменты используются. Сколько workflows осталось в каждом проекте и почему.

**MAXIBOT**

Что изменено, фактический production SHA/digest, состояние API, Poller и базы данных.

**GPOINT**

Что изменено, какие компоненты обновлены, фактические SHA/digest, состояние API, Bot, Workers, AGATA, Eros и GSales.

**REMOVED**

Точный перечень удалённых старых контроллеров, workflows, скриптов и конфигураций.

**SAFETY**

Проверки разрешений, миграций, резервных копий, Workers и независимости проектов.

**PERFORMANCE**

Замеренное время прежних и новых релизов. Реальный выигрыш или оставшиеся задержки.

**FINAL STATUS**

- `COMPLETE` — оба проекта переведены и проверены, старая система удалена.
- `PARTIAL` — часть безопасных этапов завершена, но полная миграция не подтверждена.
- `BLOCKED` — дальнейшие операции небезопасны или не разрешены.

Не заявлять `COMPLETE` без подтверждённого фактического результата.

# ОКОНЧАТЕЛЬНОЕ АРХИТЕКТУРНОЕ РЕШЕНИЕ

**Codex + GitHub → GitHub Actions → Docker BuildKit → GHCR → OpenSSH → Docker Compose V2 → Production Verify.**

MAXIBOT и GPoint используют одну стандартную архитектуру, но собственные независимые workflows.

**Не использовать:**

- Kamal;
- Dokploy;
- Kubernetes;
- Docker Swarm;
- обязательный GitHub Reusable Workflow;
- отдельный репозиторий общих релизов;
- самописный Release Controller;
- вторую систему хранения релизного состояния.

**Главная цель — максимально простая, автоматическая и надёжная релизная система на готовых инструментах GitHub и Docker, без наследия старых контроллеров и без ослабления обязательных production-защит.**
